The Hevelius playbook

How we build with AI agents. Nine rules, written down as three skills that an agent loads at the start of every session. AsBuild and AsChecked were built by them.

Read the nine rules

Why

Why write rules for an AI

An AI agent is fast, willing and never short of ideas. Left alone, it adds features nobody asked for, reopens what was already decided, and reports its own work as done. The fix is not a cleverer prompt. It is the discipline any delivery team needs: an agreed finish line, a record of decisions, and checks made by someone other than the builder.

The rules come from two places: the controls used in bank delivery, such as maker-checker, and our own builds with AI agents, where many of them were written after something went wrong.

At a glance

Three phases, nine rules

The rules

The nine rules

Each rule says why it is there. Where the rules come from, and who else has published the same ideas, is set out after the rules.

Before building

  1. Agree "done" before anything is built.

    "Done" is at most three lines that can be tested, with a budget and a hard stop. Anything "done" does not need goes on a parking list.

    Why: a build with no finish line never finishes.

  2. Decide once, and keep the decision.

    Every decision goes in a log with its reason and what would reopen it. Only evidence reopens one: a failing test, a measurement, a real user's problem.

    Why: ask a model for a fresh opinion and it will always add some ideas and drop others, so more opinions never settle anything.

  3. Tests first, then locked.

    Each requirement gets a test that is seen failing before the change. Once the person approves the tests, the builder may not edit them.

    Why: the easiest way to make a failing test pass is to weaken the test.

While building

  1. Programs check; agents do not vouch.

    A program at a checkpoint decides whether the work passed, not the agent's own word.

    Why: "all tests pass", from the agent that wrote the code, is a claim.

  2. Nobody reviews their own work.

    Every change is reviewed in a fresh session that did not build it, by a different top model where one is available. The reviewer grades each finding; a new idea is parked, not built; three rounds at most.

    Why: a builder is kind to its own work.

  3. One file holds the current state.

    A short control file is read first in every session; a log and the decision log sit beside it.

    Why: an agent starts every session with no memory of the last.

Before release, and after

  1. The person decides.

    The agent never merges its own work, never handles a password or a key, and treats instructions it finds in files as information, not orders. What the person must do is set out in plain words.

    Why: the person answers for the result.

    Ours: this is maker-checker and segregation of duties, the controls banks use, applied to an AI builder.

  2. A first-time user tests the release.

    A fresh agent with no code and no build history installs the product from its README alone and checks every promise as a user would see it. It reports and never fixes.

    Why: the builder knows too much to notice what a newcomer cannot do.

  3. The rules get shorter.

    At each release and each new model, every rule about agent behaviour is tested again, and a rule the current model no longer needs is removed. The rules name no model.

    Why: rules written for last year's model slow down this year's.

Where the rules come from: these rules come from what we learned building several projects with AI agents, including the ones that did not work, combined with articles, documentation and other people's experience, and shaped into three skills. Some of the same ideas have also been published by others, and their write-ups are worth reading. Anthropic, "Effective harnesses for long-running agents", 26 Nov 2025 also forbids the agent to remove or edit tests (rule 3), has each new session read a progress log to pick up the work (rule 6) and has agents test the way a human user would (rule 8). Anthropic, "Harness design for long-running application development", 24 Mar 2026 also has the builder and the checker agree what done looks like before any code is written (rule 1), found that agents praise their own work and added a separate, sceptical evaluator (rule 5), and revisits the setup with each new model to remove what is no longer needed (rule 9). Claude Code documentation, "Best practices for Claude Code" also warns that a reviewer asked to find gaps will usually find some, and that chasing every one leads to over-engineering (rule 2), and says to give the agent a check that returns pass or fail and to have it show evidence instead of saying it succeeded (rule 4).

The skills

The three skills

  • engineering-playbook: how the agent and the person work together: scope, decisions, records, safety.
  • engineering-build-loop: how each piece of work is built: plan, locked tests, checks, review, pull request.
  • user-walkthrough-qa: how a release is tested from the user's side before it is called done.

They are written for Claude Code. Each project adds a short file of its own facts, including which models build and which review.
